# football-sim カットシーン量産システム v1

作成日: 2026-08-27
位置づけ: Phase 1で採用した正本設計。制作方式・認定階層・停止線を全カットシーンに適用する。

## 1. 結論

ショートパスF4を画像生成の反復で仕上げる方式は終了する。今後の全カットシーンは、次の責務分離で生産する。

1. **動作・左右・遮蔽・頭身**: 動画の時間情報と3D/2Dリグで決定論的に固定する。
2. **人物の領域**: 頭、肌、シャツ、パンツ、ソックス、スパイクを部位IDマスクとして固定する。
3. **画風**: 採用済みF2/F3・クロス・heading系から抽出した、輪郭・セル陰影・折り目デカールの規則で描く。このシェーダーは未実証なので、F2/F3再現試験を通るまで採用扱いにしない。
4. **顔と髪**: 向きクラス別の正典ヘッドを首アンカーへ合成する。右プロフィールは刈上げ正典を使う。
5. **ボール・移動・カメラ・速度線・インパクト**: ゲーム側で独立して合成・アニメーションする。

画像生成モデルは、連続動作のポーズを決める工程には使わない。必要な場合も、新しい向きクラスの画風正典や静止ヒーローカットを一度作る用途に限定し、採用後は固定資産として再利用する。

## 2. 棚卸しで判明したこと

- `GAME_PLAN.md`には当初から、基本ポーズと差し替えレイヤーをランタイム合成する方針がある。
- `BACKLOG.md`のPT-07も、ポーズごとのアンカー化と「新角度が出た時だけ向きクラスを追加する」設計である。
- `sprite-studio`には、ポーズJSONから部位IDパスとライトパスをレンダリングし、ドット化して頭を合成するCT4D工程が存在する。
- CT4Dで実証済みなのは、走り6コマのポーズ連続性とちらつきゼロだけである。採用済みマンガ画風、キック、交差脚、空中、GK、2人接触、5方向ヘッドは未実証である。
- 現在の試合描画には、ショートパス、ワンツー、ロングパス、クロス、FK、シュート、ミドル、ボレー、ヘディング、ドリブル、飛び出し、ポストプレー、タックル、GK、ファールなど多数の個別経路がある。
- 現在の画像資産は同じ動作でも1枚、2枚、4枚、6枚が混在し、制作方法も世代ごとに異なる。まず制作契約を統一しないと、今後もシーンごとに同じ問題が再発する。
- ショートパスF4の失敗は画質ではなく、強い脚の交差、奥行き、遮蔽を画像生成モデルが別ポーズへ再解釈することが主因である。

## 3. 4つの制作レーン

| レーン | 対象 | 制作方法 | 画像生成の役割 |
|---|---|---|---|
| M: Motion | 1人の連続動作 | リグ、部位ID、決定論シェーダー、ヘッド合成 | 新向きの正典作りだけ |
| D: Duel | 攻守2人の競り合い | Mを人物ごとに同じ世界座標で生成し、身体部位単位の深度と接触アンカーで合成 | 原則使わない |
| H: Hero | 得点、歓喜、負傷、退場、交代などの静止カット | 採用済み正典を固定して再利用 | 新規の一枚絵のみ使用可 |
| P: Procedural | ボール飛行、空、ネット、速度線、インパクト、HUD | Canvas描画と背景素材 | 不要 |

連続動作をHレーンで作らない。1対1を一枚の生成画像へ焼き込まない。ボール軌道を人物画像へ焼き込まない。

## 4. 演出全体の方式マトリクス

| 演出群 | 現在の主な資産/経路 | 採用レーン | 共通化する動作ファミリー | 次の扱い |
|---|---|---|---|---|
| 走り・ドリブル・飛び出し | `manga_run6`, `manga_dribble*` | M | LOCOMOTION | CT4D実証済み走りを画風較正の第2基準にする |
| ショートパス・ワンツー | `manga_shortpass*`, onetwo | M + P | GROUND_KICK / RECEIVE | F2/F3/F4を最初の量産ベンチマークにする |
| ロングパス・クロス・FK | `manga_longpass`, `manga_cross6`, FK2拍 | M + P | GROUND_KICK | 蹴り脚、接触点、ボール飛行を別契約に分離する |
| トラップ・受け | onetwo受け、既存M-04資料 | M + P | RECEIVE | 胸受け・足元受けを別アンカー列にする |
| 通常シュート・ミドル | `manga_shot*`, 採用4コマ | M + P | STRIKE | 採用4コマを画風基準にし、ポーズはリグへ移植する |
| ボレー・オーバーヘッド | longpass流用、`manga_overhead5` | M + P | AIR_STRIKE | 空中姿勢用の奥行きクラスを使う |
| ヘディング | `manga_heading6`, `headingdef4`, rise duel | M/D + P | AERIAL_HEADER | 攻守を別人物として生成・合成する |
| タックル・ポストプレー | `manga_tackle*`, `postplay*` | M/D | TACKLE / CONTACT | 攻守の遮蔽順をシーンJSONで固定する |
| GKダイブ・セーブ | `manga_gk_dive*` | M + P | GK_DIVE | GK専用体型・手袋・ゴール座標を別契約にする |
| ファール・カード | referee/foul系 | H + P | REACTION | 静止正典と動的ラベルで構成する |
| 負傷・歓喜・交代 | 一部未整備 | H または短いM | REACTION | 動作が必要な場合だけM、通常はHで作る |
| ボール飛行・ネット・空の間 | コード描画/背景 | P | なし | 人物制作から完全分離する |

「1アクション=固有の全身画像セット」ではなく、8個前後の動作ファミリーへパラメータを与える構造にする。

## 5. 向きと奥行きのクラス

向きクラスはポーズ数と独立して管理する。新しいアクションが既存の向きで成立するなら、新規ヘッドや新規画風正典は作らない。

### 初期向きクラス

- `PROFILE_R`: 右向き真横。刈上げ右プロフィール正典を使用。
- `THREEQ_R`: 右向き3/4。
- `FRONT`: 正面寄り。
- `THREEQ_L`: 左向き3/4。
- `PROFILE_L`: 左向き真横。

背面が必要になった時だけ`REAR`を追加する。左右反転は身体の動作確認には使えるが、顔・髪・利き足ラベルの正本には使わない。

### 奥行きクラス

- `PLANAR`: 手足の前後差が小さい通常姿勢。
- `CROSSED`: 手足が体前面で交差し、遮蔽順が重要。ショートパスF4〜F6を含む。
- `AERIAL`: 空中・強い短縮遠近。ボレー、ヘディング、オーバーヘッド。
- `GROUND`: スライディング、負傷、膝スライド。

F4を通常の横向きポーズとして処理しない。`PROFILE_R + CROSSED`の最初の正典として扱う。

## 6. 座標・解像度契約

旧`CT4_STYLE_SPEC.md`の256×224・8pxタイル方式と、現在採用中のマンガスプライト190px方式を同時に検査しない。今回使うのはCT4Dの**ポーズ・ID・ライト出力機能**であり、旧CT4の画風・解像度を完成仕様として採用するわけではない。

| 段階 | 座標/寸法 | 補間 | QA |
|---|---|---|---|
| Source rig | 3Dワールド座標＋関節角 | なし | 骨長、左右ID、接地、接触点 |
| Pose render | 十分な解像度のID/ライトパス | ラスタライズ | 部位ID、遮蔽、シルエット |
| Sprite logical | 全身高190 logical pxを基準 | 面積平均で一度だけ縮小後、パレット量子化 | 1px輪郭、色数、部位輪郭、頭身 |
| Export/review | logical spriteの整数倍 | nearest-neighborのみ | 画素を変えるQAは行わない |
| Runtime scene | 現行カットシーンcanvas | `imageSmoothingEnabled=false` | 見切れ、攻撃方向、ボール同期 |

画風プロファイル名を`MANGA_190_V1`とし、旧CT4の8pxタイル基準は適用しない。将来SFC方式を別に採用する場合は`CT4_SFC_V1`として別プロファイルにする。

## 7. 1フレームのデータ契約

各フレームは完成PNGだけでなく、次の再生成可能な情報を持つ。

```json
  "viewClass": "PROFILE_R",
  "depthClass": "CROSSED",
  "character": {
    "bodyPreset": "outfield_male_v1",
    "skinTone": "skin_03",
    "headSet": "01_spiky_twoblock",
    "hairStyle": "spiky_twoblock",
    "expression": "focused",
    "kitTemplate": "standard_outfield_v1",
    "goalkeeper": false,
    "gloves": false
  },
  "supportLeg": "left",
  "kickingLeg": "right",
  "visibleLimbs": ["rightArm", "leftThigh", "leftShin", "rightThigh", "rightShin"],
  "occlusionOrder": ["torso", "leftThigh", "rightThigh", "leftShin", "rightShin"],
  "ballContact": { "phase": "post-contact", "foot": "right" },
  "poseFile": "...json",
  "semanticMasks": {
    "shirt": "...png",
    "shorts": "...png",
    "skin": "...png",
    "socks": "...png",
    "boots": "...png"
  },
  "headCanon": "spiky_twoblock_profile_R"

```

左腕が完全に隠れるフレームは、`visibleLimbs`から左腕を外す。モデルや補間処理に推測させない。

### 7.1 2人接触シーンの追加契約

Dレーンは人物を単純な前後2枚として扱わない。シーン単位で次を持つ。

```json
{
  "camera": { "projection": "orthographic", "viewClass": "THREEQ_R" },
  "actors": {
    "attacker": { "root": [0.0, 0.0, 0.0] },
    "defender": { "root": [0.2, 0.0, -0.1] }
  },
  "contacts": [
    { "a": "attacker.head", "b": "ball", "maxDistancePx": 2 },
    { "a": "attacker.shoulder", "b": "defender.shoulder", "maxDistancePx": 4 }
  ],
  "partDepthOrder": [
    "defender.torso", "attacker.leftArm", "attacker.torso", "defender.rightArm"
  ]
}
```

共通カメラ、root座標、接触アンカー、部位単位の深度順、許容接触距離を固定する。ヘディングやタックルで前後関係が途中で入れ替わる場合は、フレームごとに`partDepthOrder`を明示し、接触点を通らない瞬間反転を禁止する。

## 8. 決定論レンダリング工程

1. **動作抽出**: 動画を前後込みで追跡し、左右の身体IDを時系列で固定する。
2. **キー姿勢選定**: 接触、タメ、振り抜き等の意味のある瞬間を選ぶ。均等時刻だけで選ばない。
3. **リグ適合**: 承認骨格へ3D/2Dリグを合わせ、接地高とカメラを全フレーム共通化する。
4. **ID/ライトパス**: CT4Dで部位IDと陰影を別々にレンダリングする。
5. **セマンティックマスク**: シャツ、パンツ、露出肌、ソックス、スパイクを別マスクで保持する。
6. **画風シェーダー（未実証。F2/F3再現で認定する）**:
   - 外周1pxの黒輪郭
   - 部位ごとにベタ＋影＋必要時だけハイライト
   - 肘・膝の曲げ角に応じた短い関節線
   - シャツとパンツの折り目デカール
   - 32色以内、アンチエイリアスなし
7. **頭部合成**: 向きクラス別ヘッドを首アンカーへスタンプする。
8. **出荷処理**: 190px基準、透明背景、余白、MangaRecolor色相窓を検査する。
9. **ゲーム合成**: ボール、移動、カメラ、FX、攻守色を実行時に加える。

採用済み画像のテクスチャを放射状に引き延ばして別ポーズへ貼る処理は使わない。画風はテクスチャ転写ではなく、パレット・輪郭・陰影・デカールの規則として移植する。

## 9. 自動QAゲート

### 9.1 フレーム単体

- 左右ID、軸足、蹴り足、身体の向きが契約と完全一致する。
- 非表示指定の腕・脚を描かない。
- 頭身は5.40〜5.80H。同一シーケンスの頭高差は3%以内。
- 全主要関節の承認座標との差を測る。閾値はF2/F3の採用画像と承認トレースの実測から較正し、テストmanifestへ固定する。
- 部位ごとにマスクIoU、輪郭の95% Hausdorff距離、投影骨長、面積比を測る。F4では左右の腿・下腿・ソックス・スパイクを別々に判定する。
- 承認セマンティック面との遮蔽境界一致率を測る。関節点が合っていても、脚の太さ、短縮遠近、膝から足首の輪郭が違えばFAILとする。
- シャツ、パンツ、肌、ソックス、スパイクの各マスクが独立し、隣接部位へ色が漏れない。
- 190px表示で輪郭が1px、全体32色以内、アンチエイリアスなし。
- 透過出荷なら背景不透明画素0。比較シートなら背景は厳密なRGB(255,255,255)。

### 9.2 連続性

- 左右IDの入れ替わり0件。
- 隣接フレームで遮蔽順が変わる場合、関節軌道が交差点を通過していること。
- 頭、骨盤、肩幅、脚長がフレーム間で不連続に変わらない。
- F5とF6のように近い姿勢は、画像差分も小さく、変化箇所が動作上妥当であること。
- ボール接触前後で、足とボールの距離が単調に接近してから離れること。

### 9.3 2人接触

- 接触アンカー間の距離がシーン契約内である。
- 人物同士の不正な貫通面積が閾値以下である。
- 部位単位の深度順が契約と一致する。
- 前後関係が切り替わるフレームでは、接触点と軌道が連続する。

### 9.4 ゲーム内

- team1/team2の両方で、人物がボール進行方向を向く。
- ネイティブ向き、スプライト反転、攻撃方向のXOR契約を自動テストする。
- 667×375、800×360、844×390、1280×720で見切れなし。
- 画像decode前に時計を開始しない。破損・timeout・detachで有限停止する。

### 9.5 提示ゲート

機械QAと独立目視QAのどちらかがFAILなら、候補としてユーザーへ提示しない。同じ方式で3回FAILしたら、その方式を停止し、パラメータ調整を続けない。

## 10. 認定階層

一枚の合格を、量産システム全体の合格と言い換えない。

| 認定レベル | 合格に必要なもの |
|---|---|
| Frame | 1フレームのポーズ・輪郭・画風・ID・頭身QA |
| Sequence | 隣接フレームの左右ID・遮蔽・骨長・動作連続性 |
| Pose class | 同じ`viewClass + depthClass`のheld-out poseを1つ通す |
| Action family | 同じファミリーの別アクションまたは別シーケンスを通す |
| Lane | そのレーンの直交canaryをすべて通す |
| System | M/D/H/P各レーンのcanaryを通す |

## 11. F4ベンチマーク

F4は`PROFILE_R + CROSSED + GROUND_KICK`の認定試験とする。

### 入力

- 承認済み時間追跡骨格
- 承認済み全身セマンティックトレース
- F2/F3採用画像
- 5.6頭身体型カノン
- 右向き刈上げヘッド正典

### 合格条件

1. 承認トレースの両脚の交差、膝、足首、右腕、体幹傾斜を満たす。
2. 左右の脚IDを前後フレームから維持する。
3. F2/F3と同じ人物、頭身、輪郭、セル陰影に見える。
4. F3→F4の軌道として連続する。

F4合格はFrame認定であり、量産方式の認定ではない。F4をユーザーが採用した後、初めてF5をheld-out poseとして制作できる。F5が同じ工程で合格した時点で`PROFILE_R + CROSSED`をPose class認定する。一枚限りの手修正は、F4が似ていても認定対象外とする。

## 12. システム全体の直交canary

ショートパスだけで全方式を認定しない。最低限、次を個別に通す。

| Canary | 検証対象 |
|---|---|
| F4→F5 | `GROUND_KICK / PROFILE_R / CROSSED`、片腕遮蔽、交差脚 |
| 走り6コマ | `LOCOMOTION / THREEQ_R / PLANAR`、ループ、接地、ちらつき |
| ヘディング攻守 | Dレーン、共通カメラ、接触アンカー、部位深度、空中 |
| GKダイブ | GK体型、手袋、ゴール基準座標、横長シルエット |
| 静止リアクション1枚 | Hレーン、正典固定、人物差分、ユーザー採用フロー |
| ボール飛行ビート | Pレーン、人物非依存、カメラと軌道 |

全canaryを通るまで「全カットシーン量産システム認定済み」としない。

## 13. 資産manifest

各出荷資産は、完成PNGだけでなく次をmanifestへ記録する。

- `actionFamily`, `viewClass`, `depthClass`, `styleProfile`
- source pose、部位ID/マスク、head set、character preset、kit template
- 採用者・採用日・SHA-256
- Frame/Sequence/Pose class/Action familyの認定状態
- mirror可否、ネイティブ向き、利き足、visible limbs、接触アンカー
- 却下入力と再利用禁止候補

F2は台帳上採用済みで、Phase 1では正本パスとSHAをmanifestへ固定し、tracked状態をゲートで検査する。F3と同様に、採用済みであることと再現可能に保存されていることを分けて検査する。

## 14. 実装順

### Phase 1: authority固定（候補評価は未実装）

- 採用済みF2を正本パスへ固定し、SHAロックする。
- F2/F3/F4の骨格、向き、遮蔽、authority pathとSHAを一つのテストパックにする。
- F2/F3のsemantic masks、輪郭測定、部位metricsはPhase 2の較正済み評価器で作る。Phase 1では自己申告metricsを受け付けない。
- 評価thresholdsはPhase 1のmanifestに置かず、Phase 2でground-truthを較正した後に初めて追加する。
- 現行`shortpass_approval_gate.py`のgeneration経路は失効させ、build-compositeの承認素材検証だけを維持する。
- `MANGA_190_V1`のlogical/export/runtime座標をmanifestへ固定する。

### Phase 2: 画風シェーダー較正

- CT4Dはgeometry-onlyでF2/F3再現準備を行う。ID/ライトパスからF2/F3の輪郭・陰影・パレットへ寄せる工程はPhase 2の較正対象とする。
- F2/F3を再現できないシェーダーをF4へ進めない。

### Phase 3: F4認定

- 承認リグからF4を決定論レンダリングする。
- 自動QAと独立QAを通過した時だけ、トレース上下比較として提示する。

### Phase 4: CROSSED pose class認定

- F4採用後、F5をheld-out poseとして同じ工程で制作する。
- F5合格後に限り、F6、クロス、ロングパス、FKへ同じ動作ファミリーを適用する。
- 新しい角度が必要な場合だけ向きクラスを追加する。

### Phase 5: 直交canary

- 走り、ヘディング攻守、GK、静止リアクション、ボール飛行を順に認定する。
- canaryがFAILした場合、ショートパスの成功を根拠に横展開しない。

### Phase 6: 他ファミリー

- STRIKE → RECEIVE → AIR_STRIKE → TACKLE/CONTACTの順に認定する。
- 各ファミリーで最難関1シーンとheld-out poseを通してから量産する。

## 15. 今回の停止線

- Phase 1 authority gate合格後であっても、Phase 2の較正完了前に新しいカットシーン画像を生成しない。
- ショートパスのコマ数を制作上の都合で削らない。コマ数は演出テンポと動作の意味から決める。
- F4認定前にF5/F6や別シーンの画像制作へ進まない。
- 設計採用後も、試合画像の最終採否は従来どおりシーンごとのユーザー目視ゲートを維持する。
